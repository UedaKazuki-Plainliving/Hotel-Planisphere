### セッション記録

#### 仮説 D-1：プラン一覧はAjaxで動的に取得しているため、特定の条件下でロードに失敗する

**テスト手順：** plans.html の HTML ソースを静的に取得し、プランがどのように描画されているか確認する

**観察結果：**
- 静的HTML取得時、表示プランは1件のみ（「お得な特典付きプラン」）
- ページ下部に "Loading..." テキストが残留している
- about.html によると「Ajax非同期取得・ログイン状態と会員ランクで表示プランが変動」と記載
- 実際のプラン総数は10件（about.html記載）

**次の仮説：** JavaScriptが無効な環境（古いブラウザ、一部の自動テストツールの設定）ではプラン一覧が1件しか表示されないのではないか → **BUG-005** として記録

---

#### 仮説 D-2：reserve.html は plan-id パラメータで動作するが、不正な値のハンドリングが実装されていない可能性がある

**テスト手順：** 以下3パターンのURLにアクセス
- `reserve.html`（plan-id なし）
- `reserve.html?plan-id=999`（存在しないID）
- `reserve.html?plan-id=0&username=admin`（追加パラメータ）

**観察結果：**
- いずれのURLでも予約フォーム自体は表示される
- plan-id が無効でもエラーページへの遷移なし
- フォームの「プラン名」部分が空白またはデフォルト表示になると推測される
- 追加パラメータは無視される（DOM汚染なし）

**次の仮説：** プラン名が空の状態で予約を完了できてしまうのではないか → **BUG-010** として記録

---

#### 仮説 D-3：マイページにはファイルアップロードとJavaScriptダイアログがあり、確認画面のBootstrap Modalと競合する可能性がある

**テスト手順：** about.html の記述を詳細確認
- "マイページ：ファイルアップロード、JavaScriptダイアログ（confirm/alert）機能"
- "予約確認画面：Bootstrap Modalダイアログ（フェードインアニメーション付き）"

**観察結果：**
- マイページでのJS alert/confirmはネイティブダイアログ
- 予約確認はBootstrap Modal（独自実装）
- 2種類のダイアログ技術が混在している

**次の仮説：** マイページのJSダイアログは、一部のブラウザでBootstrap Modalと競合して操作不能になる可能性がある → **BUG-012** として記録

---

#### 仮説 D-4：confirm.html（予約確認ページ）はURLを直接知っていれば認証なしでアクセスできる

**テスト手順：** `confirm.html` を直接URLで取得（ログインなし）

**観察結果：**
- アクセス可能（ページが表示される）
- 404・403・ログインページへのリダイレクトなし
- 予約確認用のフォーム・モーダルが表示状態

**次の仮説：** mypage.html も同様に認証なしでアクセスできるのではないか → **BUG-002 / BUG-003** として記録（セキュリティ観点④に詳述）

#### 仮説 D-5：会員登録フォームの「会員種別」ラジオボタンのデフォルト選択が不明確

**テスト手順：** signup.html のフォーム構造を取得し、ラジオボタンの checked 状態を確認

**観察結果：**
- 会員種別ラジオボタン（プレミアム/一般）のデフォルト選択が HTML から特定できない
- デフォルトが「プレミアム会員」の場合、意図せずプレミアムで登録するユーザーが発生する可能性
- デフォルトが「一般会員」の場合は一般的に問題ない

**次の仮説：** デフォルト選択の状態によっては意図しない会員種別での登録が起きる → **BUG-019** として記録

### セッション記録

#### 仮説 M-1：宿泊数や人数に負の値・小数・ゼロを入力するとシステムが誤動作する

**テスト手順：** reserve.html の宿泊数・人数フィールドに以下の値を順に試す

| 入力値 | フィールド | 期待動作 |
|---|---|---|
| `-1` | 宿泊数 | バリデーションエラー |
| `0` | 人数 | バリデーションエラー |
| `1.5` | 宿泊数 | バリデーションエラーまたは切り捨て |
| `9999` | 人数 | バリデーションエラー（上限値） |
| ` ` (空白のみ) | 氏名 | バリデーションエラー |

**観察結果：**
- フィールドのtype属性は `number` → ブラウザネイティブの最小値チェックは動く可能性があるが、min/max属性の明示的な設定が確認できない

- `人数: 9999` のような大きな値での金額計算結果が整数オーバーフローしないかが不明
- `氏名: " "（スペースのみ）` は required をすり抜ける可能性がある

**次の仮説：** 人数に `9999` を入力すると合計金額の計算結果が異常値になる → **BUG-018** として記録

## ④ セキュリティ観点

### 探索チャーター

> **目的：** 認証・認可・情報漏洩・通信セキュリティの観点で脆弱性を発見する。特に「ログインしていない状態でアクセスできるべきでないページ」「機密情報の露出」を重点的に探索する

---

### セッション記録

#### 仮説 S-1：【最重要】テストユーザーの全パスワードがトップページに平文で公開されている

**テスト手順：** `index.html`（トップページ）の全テキストを取得・確認

**観察結果（実際に確認済み）：**

```
ichiro@example.com   / password    （プレミアム会員）
sakura@example.com   / pass1234    （一般会員）
jun@example.com      / pa55w0rd!   （プレミアム会員）
yoshiki@example.com  / pass-pass   （一般会員）
```

これらが練習サイトのトップページと about.html の両方に掲載されている。

**分析：**
- 練習サイトとしての意図は理解できる（使い方を示すため）
- しかし、実際のサービスに類似した設計でこれが残存した場合は **致命的** なセキュリティ事故となる
- パスワードを平文で公開することは、実際のシステムでは絶対に許容されない
- 本サイトが「引っ掛かりがちな要素を意図的に配置した練習用サイト」であることを考慮しても、この点は明示的に「意図的なもの」と記載すべき

**判定：** 練習サイトとしての設計意図は理解できるが、**セキュリティ意識の観点から設計の問題として指摘する**

→ **BUG-001（致命的）** として記録

---

#### 仮説 S-2：mypage.html は未認証でアクセスできる

**テスト手順：** ログインせずに `mypage.html` へ直接URLアクセス

**観察結果：**
- ページが表示される（403 / ログインページへのリダイレクトなし）
- ログインしていなければ会員情報は表示されないが、ページ構造・フォーム・ファイルアップロード機能が露出している

**判定：** 認証チェックがクライアントサイドのJavaScriptのみで実装されている可能性が高い。サーバーサイドで認証を強制すべき

→ **BUG-002（重大）** として記録

#### 仮説 S-3：confirm.html は未認証でアクセスできる

**テスト手順：** ログインせずに `confirm.html` へ直接URLアクセス

**観察結果：**
- ページが表示される（リダイレクトなし）
- 予約確認フォームが表示状態で、「この内容で予約する」ボタンも使用可能
- 予約フォームを経由せずに直接 confirm.html から予約操作が試みられる可能性がある

#### 仮説 S-4：ログインエラーメッセージで「メールアドレス未登録」と「パスワード誤り」が区別できる場合、アカウント列挙攻撃が可能

**テスト手順：** 以下2パターンでログイン失敗時のエラーを比較

| パターン | メール | パスワード |
|---|---|---|
| A（存在しないメール）| `notexist@example.com` | `password` |
| B（パスワード誤り）| `ichiro@example.com` | `wrongpassword` |

**観察結果：**
- 以前のATDD実装（UT-013）で確認済み：両ケースで同じエラーメッセージが表示される
- これは正しい実装（アカウント列挙攻撃の防止）
- ただしエラーメッセージが「メールアドレスまたはパスワードが違います」である場合、攻撃者にどちらが間違いか分からない設計になっている

**判定：** この点は正しく実装されている → **適合（問題なし）**

#### 仮説 S-5：ログインセッションの管理（タイムアウト・Cookie属性）が不明

**観察結果：**
- セッション管理の実装詳細がHTMLからは確認不可
- サイトがHTTPS（`https://`）であることは確認済み
- Cookie の Secure フラグ・HttpOnly フラグが設定されているかは静的確認では不明
- ログアウト後のブラウザバックでキャッシュが返される可能性あり（BUG-014と連関）

**判定：** セッション管理の詳細確認が必要

→ **BUG-004（重大）** として記録

#### 仮説 S-6：HTTPS の利用は確認できるが、HTTP でのアクセス時のリダイレクトを確認する

**テスト手順：** `http://hotel-example-site.takeyaqa.dev/ja/login.html` へのアクセス試行

**観察結果：**
- サイトは `https://hotel-example-site.takeyaqa.dev/ja/` で運用されており、HTTPS化は確認済み

**判定：** HTTPS利用は確認済み（適合）。HTTP→HTTPSリダイレクトは要実機確認

### セッション記録

#### 仮説 UX-1：未ログイン状態でもナビゲーションに「ログアウト」リンクが表示されており、ユーザーが混乱する

**テスト手順：** `index.html` のナビゲーション構造を確認（未ログイン状態）

**観察結果（実際に確認済み）：**
- ナビゲーションに「ログアウト」リンクが存在する
- ログインしていない状態でも「ログアウト」が表示されている
- 同時に「ログイン」リンクも存在する
- 未ログイン時に「ログアウト」と「ログイン」が両方表示されていると矛盾した状態

**分析：**
- 神経症傾向が高い上田さんのような初級者が「ログアウト」を押すと何が起きるか不安になる
- 「すでにログインしているのか？」と誤解する可能性がある

→ **BUG-006（中）** として記録

---

#### 仮説 UX-2：パスワード入力フィールドに「表示/非表示」トグルボタンがないため、タイプミスに気づきにくい

**テスト手順：** signup.html と login.html のパスワードフィールドを確認

**観察結果：**
- パスワード入力欄は `type="password"` で入力文字が「●●●」に隠れる
- 「パスワードを表示する」トグルボタンが存在しない
- 確認用パスワード欄も同様に非表示
- 初級者がパスワードを誤入力した場合、どこが違うか確認できない

**次の仮説：** パスワードを誤入力してもエラーメッセージが「一致しません」だけでは、どちらを直せばよいか分からない → **BUG-008（軽微）** として記録

---

#### 仮説 UX-3：予約フォームの日付入力がjQuery UI Datepickerで、ブラウザネイティブのdate型でないため、入力フォーマットが分かりにくい

**テスト手順：** about.html の記述を確認 → "jQuery UI Datepicker を使用"

**観察結果：**
- ネイティブ date 型（スマートフォンでカレンダーUI表示）ではなくjQuery UIのDatepicker
- PCではカレンダーポップアップが表示される可能性があるが、キーボード入力時の形式（`yyyy/MM/dd`）をユーザーに明示しない場合、エラーになりやすい
- スマートフォンのブラウザでネイティブカレンダーが表示されない可能性

→ **BUG-022（中）** として記録

---

#### 仮説 UX-4：プラン一覧に写真がなく、テキストと金額だけでは魅力が伝わらない

**テスト手順：** plans.html のプラン一覧を確認

**観察結果（実際に確認済み）：**
- プランには「お得な特典付きプラン」「大人1名7,000円」「スタンダードツイン」という情報のみ
- 部屋の写真・設備写真・施設写真が一切ない
- ユーザークローン（上田さん）の感情マップ：「プラン一覧に写真がない → 不満・不信感」と一致

→ **BUG-023（中）** として記録（ユーザビリティ）

---

#### 仮説 UX-5：エラーメッセージが発生した際、ページ上部にスクロールしてエラー箇所が画面外になる可能性がある

**テスト手順：** 長いフォーム（signup.html）で下方のフィールドでエラーを起こした後の表示を想定

**観察結果：**
- signup.html は入力フィールドが10項目（会員種別・住所・電話番号・性別・生年月日・お知らせ）と多い
- 送信ボタンクリック後のエラー表示位置がページ上部の最初のエラーフィールドにスクロールするか不明
- エラーが電話番号欄（下の方）のみの場合、ページトップにいるとエラーに気づかない可能性

→ **BUG-024（軽微）** として記録

---

#### 仮説 UX-6：「パスワードを忘れた場合」のリンクがなく、ログインできなくなった場合の回復手段がない

**テスト手順：** login.html のページ構造を確認

**観察結果（実際に確認済み）：**
- ログインページに「パスワードを忘れた方はこちら」リンクが存在しない
- パスワードリセット機能も未実装
- 上田さんはパスワードを忘れがち（ユーザークローンの知見）
- ログイン不能になった場合、唯一の手段が新規アカウント作成のみ

→ **BUG-025（中）** として記録（ATDD の @missing-feature で既知だが、ユーザビリティ上も重大）
