### 5.3 テスト文書品質の評価

**テスト設計書・テストケースの品質評価：C（要改善）**

レビューで発見された43件の指摘事項の中で、特に深刻なのは以下の3点である。

1. **テストケース件数の誤記（REV-001）**：まとめ表に「47件」と記載されているが実際は「57件」。10件の乖離はテスト管理上重大な問題。

### 5.4 ユーザークローン効果の評価

本プロジェクトでは「上田 和樹（50代・IT管理職・初級者・神経症傾向高い・せっかち）」をユーザークローンとして活用した。ユーザークローンを使ったATDDと、使わないATDDの比較を行った結果、以下の差異が明らかになった。

| 観点 | ユーザークローン版（atdd_test_scenarios.md）| ノーペルソナ版（atdd_test_scenarios_no_persona.md）|
|---|---|---|
| リアルタイム金額計算シナリオ | 6件（「すぐ結果が見たい」特性から）| 3件（基本機能のみ）|

**ユーザークローンの効果：**

> **結論：** ユーザークローンとシステム的な機能分析は相補的であり、両方を組み合わせることで最も包括的なテスト設計が実現できる。

## 7. 次回開発への提言（Recommendations for Next Development）

### 7.1 テスト設計プロセスの改善

**提言①：テスト設計書とテストケースの同時作成を避け、レビューサイクルを挟む**

今回、テスト設計書作成後にテストケースを作成したが、設計書の誤記（パスワード）がそのままテストケースに伝播する構造になっていた。設計書→レビュー→テストケース作成という順序を徹底することで、誤記の連鎖を防ぐことができる。

**提言②：テスト件数を設計書とテストケースで自動照合する仕組みを導入する**

今回は設計書の件数サマリー（47件）と実際のテストケース数（57件）が10件ずれていた。マークダウン形式ではなくExcelまたはTestLink等のテスト管理ツールを使えば、件数の自動集計が可能になる。

**提言③：「合格基準」は設計書の冒頭に単一のソースとして定義し、他文書は参照する形にする**

性能基準が「ATDDシナリオ3秒、手動テスト5秒」と分散して矛盾した。単一の「品質基準書」または「定義集」を作成し、すべての文書がそこを参照する形にすることで、矛盾が発生しにくくなる。

---

### 7.2 セキュリティテストの強化

**提言④：セキュリティテストを専用フェーズとして計画に組み込む**

今回の探索的テストでセキュリティ問題が多数発見されたが、手動テストケースとしては1件もカバーされていなかった（OWASPカバレッジ30%）。次回は：

- テスト計画の初期段階でセキュリティテストスコープを明示する
- OWASP Testing Guideを参照した観点一覧を作成する
- 少なくとも認証・認可・入力バリデーション・セッション管理の4領域をカバーする

**提言⑤：XSS・SQLインジェクション等の脆弱性は自動化ツールで継続的に検査する**

BUG-020（XSS）のような脆弱性は、開発のたびに手動で確認するには工数がかかりすぎる。OWASP ZAP等のセキュリティスキャナーをCIパイプラインに組み込み、定期的・自動的に検出する仕組みを構築することを推奨する。

---

### 7.3 ATDD・自動テストの拡充

**提言⑥：@missing-feature の機能が実装されたらすぐにATDDシナリオをGreenにする体制を整備する**

現在7件が@missing-featureとなっている。これらは「将来実装される前提」でシナリオが書かれているが、実際に実装されたときに誰がいつシナリオをGreenにするかの担当・ルールが明示されていない。次回開発では：

- 各@missing-featureにチケットIDを紐づける
- 機能実装のDefinition of Done（完成の定義）に「ATDDシナリオがGreenになること」を含める

**提言⑦：手動テストで発見されたバグを再現するATDDシナリオをその場で作成する**

探索的テストで発見した25件のバグについて、手動確認テストケースが存在しないため再現性の確認が困難な状況にある。発見されたバグを再現するシナリオを（たとえ@known-bugタグを付けてでも）ATDDとして記録することで、修正後の回帰テストが自動化できる。

---

### 7.4 ユーザビリティ・UX品質の継続的評価

**提言⑧：ユーザビリティテストを定期的に実施し、ユーザークローンの精度を高める**

今回のユーザークローン（上田 和樹）は探索的テスト・ATDD設計において有効に機能した。しかし、クローンの定義があくまでもヒヤリングに基づく仮説であり、実際のユーザーテストによる検証は行われていない。次回開発では：

- 実際のターゲットユーザー（ITリテラシーが低い50代）に対してユーザビリティテストを実施する
- テスト結果をユーザークローン定義にフィードバックし、クローンの精度を向上させる

**提言⑨：探索的テストで発見されたUXバグを次回リリースの要件として取り込む**

BUG-006（ナビゲーション矛盾）・BUG-008（パスワード表示切替）・BUG-022（Datepicker操作性）・BUG-025（パスワードリセット）は、ユーザビリティ上の重要な問題である。これらを次回開発の機能要件として、ユーザーストーリー化して管理することを推奨する。

### 7.5 ドキュメント管理の改善

**提言⑩：テスト文書を生きた文書として維持するためのオーナーを明確にする**

今回作成したテスト文書（テスト計画書・設計書・ケース集・探索テスト報告書等）は、次回テスト実施時には陳腐化している可能性がある。特に：

- 対象サイトのURLや機能が変わった場合の文書更新
- @missing-featureが実装された場合のケース追加
- レビュー指摘事項の修正追跡

これらを担当する「テスト文書オーナー」を明確にし、定期的なレビューサイクル（例：四半期ごと）を設定することを推奨する。

## 付録：用語集

| 用語 | 定義 |
|---|---|
| ATDD | Acceptance Test-Driven Development。Gherkinシナリオを受入基準として先に定義し、それをパスするよう実装を進める手法 |
| @missing-feature | 現時点でサイトに未実装の機能に付与するCucumberタグ。実装後にテストを有効化できる |
| EP | 同値分割（Equivalence Partitioning）。入力値を「有効グループ」「無効グループ」に分け、各グループの代表値のみをテストする技法 |
| BVA | 境界値分析（Boundary Value Analysis）。境界の直前・直後の値をテストすることで境界での動作を確認する技法 |
| DT | デシジョンテーブル（Decision Table）。複数の条件の組み合わせと対応する期待結果を表形式で整理する技法 |
| OWASP | Open Web Application Security Project。Webアプリケーションのセキュリティに関するガイドラインを提供する非営利組織 |
| ユーザークローン | 特定のユーザープロファイル（年齢・IT技術・性格等）に基づいてAIが作成した仮想ユーザー。テスト設計における要求分析に活用 |
